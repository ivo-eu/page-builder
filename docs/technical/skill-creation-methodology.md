# 文档类 Skill 创建方法论

> 从 problem-retrospective 的创建过程提炼
> 日期：2026-05-22

---

## 一、问题定义

在 AI 辅助开发的工作流中，经常需要将某次问题解决过程沉淀为可复用的 skill。但 AI 在创建文档类 skill 时存在以下典型问题：

1. **目的理解偏差**：用户说"记录这个问题"，AI 可能理解为技术文档、知识沉淀、思维复盘等不同目标，产出物与用户期望不符。
2. **结构与内容混淆**：AI 把某次特有的思维过程写进模板结构，导致模板不可复用于其他场景。
3. **执行时机错误**：用户说"完善文档"，AI 理解为"重写文档"，在未确认具体改进方向时直接执行大量改动。

本文档提炼出一套标准化流程，用于指导"从问题解决过程 → 复盘文档 → skill"的完整链路。

---

## 二、标准化流程

### 阶段 1：确认目的（必须在动手之前）

在开始写任何内容之前，必须确认以下信息：

| 确认项 | 为什么重要 | 示例 |
|--------|-----------|------|
| 文档读者是谁 | 决定详略程度和专业术语密度 | "我自己" vs "团队成员" vs "开源社区" |
| 文档目的是什么 | 决定文档类型和结构 | "复盘思路" vs "技术方案" vs "操作手册" |
| 哪些内容要记录 | 决定信息采集范围 | "只记录失败的" vs "所有尝试都记录" |

如果用户没有主动说明，AI 应主动询问，而不是假设。

### 阶段 2：确定文档结构（容器与填充物分离）

文档结构 = 容器（通用模板）
文档内容 = 填充物（某次特定的过程）

设计原则：
- **容器要通用**：适用于同类目的的所有场景，不绑定某次特有的思维过程
- **填充物要具体**：记录某次场景的详细信息，包括代码、对话、决策

反面案例：
```
❌ 第一部分：猜测阶段（用户说什么→AI 改什么）
   第二部分：纠正阶段（用户纠正→AI 调整）
   第三部分：深入阶段（用户要求看代码→AI 分析）
```
这个结构把"这次的思维阶段"写进了容器，下次如果用户一开始就知道要看代码，这个模板就不适用。

正面案例：
```
✅ 一、问题前相关代码（任何场景都有"事发前的状态"）
   二、问题与解决过程（任何场景都有"尝试→结果"的循环）
   三、思维链总结（任何场景都有"谁做了什么决策"）
   四、改善建议（任何场景都有"下次怎么做"）
```
这个结构适用于任何问题解决过程的复盘。

### 阶段 3：确定质量标准（每部分的填写规范）

仅有结构不够，还需要定义每部分的填写标准，否则 AI 会按自己的理解随意填写。

质量标准应覆盖：

| 部分 | 标准 | 反面案例 | 正面案例 |
|------|------|---------|---------|
| 根因分析 | 必须解释技术原理 | "AI 误判了问题根源" | "SVG viewBox 默认 overflow:hidden，旋转后坐标超出范围被裁" |
| 失败原因 | 必须说明为什么解决不了 | "修改无效" | "容器大小只影响摆放空间，不影响 SVG 内部的 viewBox 裁剪" |
| 改善建议 | 必须可执行 | "下次贴代码优先" | "SVG 排查清单：①viewBox ②overflow ③父容器 ④transform" |
| 代码对比 | 必须保留完整的修改前/后 | 只放 diff 行 | 完整代码块对比 |

### 阶段 4：执行（先小后大）

执行顺序：
1. **先写一两个问题的样例**，让用户确认格式和深度是否满意
2. **确认后批量填写**剩余部分
3. **最后做整体调整**（加概括、加最终代码等）

不要一次性重写整个文档。小步迭代，每步确认。

### 阶段 5：提炼为 Skill

当文档定型后，评估是否值得提炼为 skill：

| 评估维度 | 值得做 skill | 不值得做 skill |
|---------|-------------|---------------|
| 场景频率 | 经常遇到同类问题 | 一次性问题 |
| 流程通用性 | 流程适用于多种场景 | 流程只适用于特定技术栈 |
| 复杂度 | 需要多步操作、有分支逻辑 | 一步就能做完 |

如果值得做 skill：
1. 从已定型的文档中提取"容器"（通用结构），去除"填充物"（特定内容）
2. 将质量标准转化为写作要求
3. 将已定型的文档作为参考样例挂到 skill 的 references 下

## 三、problem-retrospective 的创建过程作为案例

### 目的确认阶段

用户最初说"记录这个问题"，AI 没有确认目的，按技术文档标准给出了重构建议。用户纠正："目的不是科学性总结，而是复现思路供自我反省。"

教训：收到"写文档/记录/总结"类任务时，第一步必须确认文档类型。

### 结构设计阶段

AI 建议按"思维阶段"组织（猜测→纠正→深入→解决），用户指出这个结构不可复用于其他场景。最终确认用通用结构（代码分类→问题记录→思维链→改善建议）。

教训：模板结构必须和具体内容解耦。

### 质量标准阶段

第一版文档的失败原因只写了"AI 误判了问题根源"，改善建议只写了"贴代码优先"。用户逐条给出 10 项改进要求，包括"根因分析要解释技术原理""改善建议要可执行"等。

教训：质量标准要在写文档之前就确定，不是写完后让用户逐条纠正。

### 执行阶段

AI 在用户说"完善文档"时直接重写了整个文档，被用户退回。正确做法是等用户明确改进方向后再执行。

教训：大改动必须先确认，小改动可以直接做。

### Skill 提炼阶段

用户确认文档框架可行后，要求创建 skill。AI 将文档框架转化为 skill 的写作要求，将已定型的文档作为参考样例。

## 四、核心原则

1. **先问后做**。收到模糊指令时，确认目的和范围再动手。
2. **容器和填充物分离**。模板是通用容器，内容是特定填充物，不要混在一起。
3. **质量标准前置**。在写内容之前就定义好每部分的填写标准。
4. **小步迭代**。先写样例确认，再批量填写，不要一次性重写。
5. **文档先行，skill 后置**。先用实际文档验证框架是否可行，再提炼为 skill。
